要旨

Domo の開発は、ブラウザのクリックではなく VS Code ＋ コーディングエージェント ＋ Domo CLI で行える。コードを手元で書き、ローカルで確かめ、CLI/API で Domo へデプロイする。本書は、環境を 6 つ整えるところから、開発モデル・このアプリの構造・作れるものの全体像・デプロイの仕組み・エージェントの回し方までを図と表で辿る。最後に各自のコピーを作って「編集 → 公開 → 確認」を 1 周する。本番を壊さないための安全の線引きも合わせて示す。題材の在庫入出庫管理は、取引（IN/OUT）を正本に、残高はそこから作り直せる投影として設計した在庫 1 本で、1 アプリで Domo の複合開発を一望できる（分解は §3）。

事前課題（当日までに・15〜30 分）

当日の朝に慌てないよう、家で「緑」にしておく

「緑」＝準備 OK（信号の緑＝進んでよい）の状態。下の項目がすべて済めば緑で、これは §1 末尾のやってみよう①（6 つの点検）を家で先に済ませておくもの。

はじめに確認：当日使う端末にソフトを入れられるか（会社管理 PC は winget や npm install -g が禁止のことがある）。入れられないときは、事前に情シスへ申請するか、貸与端末・管理者権限ターミナルを手配する（迷ったら運営へ）。

  1. 公開toolkitをcloneし、reference-architectures/ 内のinventory-management-app フォルダを分かる場所に置く（§1「そろえる 6 つ」STEP 1）。
  2. VS Code とエージェント拡張を入れて、サインインできる（§1「VS Code を入れて、フォルダを開く」「エージェント拡張を入れる」）。
  3. Node・Python・Git・Domo CLI を入れて、domo login まで通す（§1「Node・Python・Git を入れる」「Domo CLI を入れて、ログインする」）。
  4. domo-ai-toolkit を clone して、疎通スクリプトが通る（§1「土台を置く」）。
  5. 開発者トークンを発行し、環境変数（DOMO_INSTANCE / DOMO_DEVELOPER_TOKEN）に設定する（§1「②の認証を整える」。管理者権限が要る。運営が検証用 DataApp を配る回は不要なことがある＝§1「運用の代替」の注記。管理者権限が無ければ無理せず運営へ）。
  6. Google Chrome を入れ、node tests/layout/shoot.mjs を 1 回動かして PNG が出ることを確認（§7）。
  7. （任意・人数が多い回は推奨）~/handson-inventory へコピー → id を外す → domo publish まで済ませる（§7）。

当日は「点検（起点プロンプト）→ 実習」に集中できる。会場と自宅ではネットワークが違うことがある（社内プロキシ／SSO／証明書）。ネットワーク起因の詰まりは、自分で粘らず早めに運営へ（講師なしで独習するときは §10「困ったとき」を見る）。

家で1 回で済む「一括点検」

やってみよう①の点検のうちツールの版と domo loginは、§1 のミニ実習①「点検のまとめ」を家で 1 回貼れば一度に済む。node / python3 / git / domo の版とログイン済みかが1 枚の表で分かる。

撤退ライン：どこまで粘るか

自分で直す＝打ち間違い・パス・環境変数・ログインのやり直し。撤退＝社内プロキシ／SSO／証明書エラー、管理 PC のインストール禁止、トークン発行に要る管理者権限が無い。設定を変えても同じエラーが出るなら環境・権限側で、自分では直せない合図。目安 15 分で糸口が無ければ、自社の情シス／Domo 管理者（当日は運営）へ回す。

事前準備：はじめる前に、6 つ整える

開発は Domo の外側（VS Code とコーディングエージェント）で行う。下の 6 つを上から順にそろえれば、あとはエージェントが公開まで進められる。所要 20〜30 分（＋セットアップ後のミニ実習 10 本は任意）。特別な環境は要らない（配布キットは外部 CDN に依存せず、画面ライブラリ vendor/domo.js も同梱＝アプリ側は追加ダウンロードなしで動く）。

本書の your-company は自分の Domo インスタンス名（例: acme）に置き換えて読む。https:// やパスは外してドメインだけ（当日の案内や、ログイン画面の URL で確認できる）。訓練用・サンドボックスのインスタンスがあればそちらを優先。本番しか無い場合は §8 のガードを全員で確認してから進む。別インスタンスが無くても、§7 で付ける名札（INVENTORY_SANDBOX_SUFFIX）が同じインスタンス内で自分の資産を本番・他参加者と分けるので、まず §8 を読んでガードを理解してから進める。

そろえる 6 つ（この順に進める）

＋もう 1 つ、Google Chrome（実習の「PNG 目視」テスト shoot.mjs が使う。Chrome さえ入れれば追加のインストール作業は不要＝スクショ用の npm パッケージも要らない）。Edge しか無い端末は §10 の FAQ を参照。PNG は既定で /tmp/inv-shots/（Windows なら C:\tmp\inv-shots\）へ出る。実行時に表示される実パスを見るか、node tests/layout/shoot.mjs --out ./_shots で見える場所へ。

権限とトークン（デプロイの前提）

管理者権限で行う

アプリ作成・カード埋め込みができる権限が要る（データフロー実行は本ハンズオンでは不要・一般開発では必要）。無い場合は管理者に依頼する。

認証は 2 系統ある

① domo コマンド（publish 等）＝domo login で動く（開発者トークンの発行は不要）。② Python の配備スクリプト（provision_domo.py）＝開発者トークン＋DOMO_INSTANCE が必須（ryuu に該当コマンドが無い面だから）。ここが最大のつまずき。

トークンは貼らない

チャット・コミットに残さない。CLI 設定領域か gitignore 済みファイルにだけ置く。

domo login と 開発者トークンの違い（認証の 2 系統）

domo login は既定でブラウザ SSO（シングルサインオン）（方式は会社の IdP による）だが、-t で開発者トークン認証も可＝「CLI は必ず SSO」ではない。一方 Python の配備スクリプトは開発者トークン＋インスタンス名を環境変数から読む。どちらも「あなたの権限」で動く。本当の違いは《使う道具》と《資格情報の寿命》の 2 軸だけで、「片方でしかできない」は“能力の壁”ではなく“どの道具がどの面に届くか”（下の表＝しくみ／その下の 2 枚＝担当範囲）。

一方だけでできること（担当範囲）

下の 2 枚が各道具の担当範囲。重なる面（Custom App design）もあるが、大半は『ryuu にコマンドがある面＝左』『ryuu に無く REST（開発者トークン）で届く面＝右』で分かれる。右の「できない」の多くは“能力の壁”ではなく道具の都合（ryuu にコマンドが無い／付属スクリプトがトークンしか読まない）。

「トークンは正しいのに動かない」

文字列を疑う前にエラー番号で切り分ける。
401＝トークン未設定／無効／インスタンス不一致（発行先＝DOMO_INSTANCE が一致するか確認）。
403＝認証は通ったが権限不足（App Studio 作成・埋め込みの権限が要る）。

「開発者トークン」の取り違え

発行は 管理 → セキュリティ → アクセストークン。developer.domo.com で作る client_id／secret（OAuth2 クライアント）は別物で、本教材では使わない。トークンはパスワード同様に扱う（共有・スクリプト直書き・コミット禁止）。

②の認証を整える：トークン発行と環境変数

埋め込み（provision_domo.py app-studio）やデータ配備のスクリプトは、domo login ではなく 開発者トークン＋インスタンス名を環境変数から読む。当日ここで止まらないよう、先に発行して設定しておく（管理者権限が必要。無い場合は運営、講師なしなら自社の Domo 管理者に依頼）。

  1. 発行Domo の 管理（Admin）→ セキュリティ → アクセストークンで「Domo アクセストークン」を新規発行し、表示された文字列をコピーする（画面を閉じると再表示できない）。
  2. 設定自分の OS のブロックをコピーし、<発行したトークン> と your-company を置き換えて実行する（山カッコ < > ごと置き換え・カッコは残さない。ターミナルを閉じると消える一時設定。実運用では環境ファイルへ）。
  3. 確認2 つの変数が設定できたか点検する。かんたんなのは下のプロンプトをエージェントに渡す（トークンの値は表示させない）。手元で確かめるなら python3 -c "import os;print(bool(os.environ.get('DOMO_DEVELOPER_TOKEN')), os.environ.get('DOMO_INSTANCE'))" を実行し、True とインスタンス名が出れば OK。
Windows（PowerShell） 
# 開発者トークンで Python スクリプトを動かす準備（この PowerShell で有効）
$env:DOMO_INSTANCE="your-company.domo.com"
$env:DOMO_DEVELOPER_TOKEN="<発行したトークン>"
macOS（ターミナル / Git Bash） 
# 開発者トークンで Python スクリプトを動かす準備（このターミナルで有効）
export DOMO_INSTANCE="your-company.domo.com"
export DOMO_DEVELOPER_TOKEN="<発行したトークン>"
設定を点検するプロンプト（値は表示しない） 
環境変数 DOMO_INSTANCE と DOMO_DEVELOPER_TOKEN が設定されているか点検して。
トークンの値そのものは表示せず、「設定あり／なし」と DOMO_INSTANCE のインスタンス名だけ教えて。

運用の代替：運営が参加者ぶんの検証用 DataApp を事前に用意できる場合、参加者は domo publish（=トークン不要）だけで反映を確認できる。トークン発行を当日の律速から外せるので、人数が多い回ではこちらを推奨。

ひとりで進めるとき（講師・運営なし）

管理者権限やトークンが無くても、編集 → node --check → PNG 目視（shoot.mjs）→ domo publish（domo login で可）＋ 読取調査まで一人で回せる。ソロで唯一塞がるのは App Studio への埋め込み（provision_domo.py app-studio＝管理者トークン）だけ。埋め込みが無くても編集→publish＋PNG で成果は確認できる。

詰まったら

ネットワーク／権限で詰んだら、運営（いなければ自社の Domo 管理者／情シス）へ。共有 AppDB を誤操作したら再実行・削除せず、そのまま管理者へ。

フロントエンド と バックエンド（責務の分担）

「どこで開発するか（外／内）」とは別に、動くもの自体も フロントエンド（画面） と バックエンド（サーバー・データ） に分かれる。画面は信用しすぎない――守る判断と重い処理はバックエンドに置くのが要。たとえばマスタを削除してよいか（物理削除＋連鎖で元に戻せない）や同じ入出庫を二重に数えないか（request_id で冪等）といった最終判断は、画面の JS ではなく inventory_api（Code Engine）が下す。

この分担がこのアプリの背骨：フロント（Pro Code）＝表示、バック（CE／ETL／Workflow／AppDB）＝守る・計算・保存。画面のチェックは“親切”（入力ミスをその場で気づかせる）、サーバーのチェックは“約束”（画面を飛ばして API を直接叩かれても効く）。だから守りは必ずバックにも置く。中身は §3 で分解する。

どれを使う？ ― フロント／バックの使い分け 10 例

Domo は画面側（フロント）にもサーバー側（バック）にも多くの機能がある。迷ったら「重い処理・守る判断・溜める記録はバックへ、見せる・操作させるはフロントへ」。よくある場面を「こうしない → こうする」で並べた。

外部DB・外部バックエンド・外部APIに依存しない。認証も保存も分析も、すべて 1 つの Domo の中で完結する（All-in-One）。

Code Engine が保存前に強制する書き込み手順

  1. 前提request_id で二重登録を弾く（冪等）。通信が再送されても在庫は二重計上されない。
  2. 検証マスタ・権限・数量・現在庫を確認。1 つでも満たさなければ拒否。
  3. 操作TRANSACTION を追記（＝正データ・append-only）。
  4. 操作BALANCE / ALERT_STATE を再計算・更新。
  5. 確認閾値をまたいだ時だけ ALERT_HISTORY を記録し、CE が通知 Workflow を起動して結果（STARTED／FAILED）を同じ行へ確定。

TRANSACTION は書き換えない正本（append-only）。訂正は逆仕訳（反対方向の IN/OUT）で追記する。不整合時は符号付き数量の合計から BALANCE を再構築する（RECALCULATE）。取引種別は入庫(IN)／出庫(OUT)の 2 種のみ。

サーバ契約（Code Engine）― 公開 1 関数 : N 操作

画面（Pro Code）は書き換えられる前提で扱い、守るべき判断はすべてサーバ側の Code Engine に集約する。フロントは 1 種類の操作関数 inventory_api(operation, request) だけを呼び、実際の可否はサーバが決める（実装は非公開 _ 始まりヘルパー 6 件に束ねる）。画面がどの経路でこの関数を呼ぶかは、後述の「画面はどう呼ぶ？」で整理する。

フロントの検証は素通りされ得る。最終判断はサーバにしか置けない。

冪等性

request_id で二重送信を無効化。通信再送でも在庫は狂わない。

再構築可能

画面はどう呼ぶ？ ― 3 つの経路の使い分け

同じ画面（Pro Code）でも、用件によって呼び方（経路）を変える。目安は「見るだけ＝直接 DataSet」「その場で確定する更新＝直接 Code Engine」「時間のかかる通知・AI＝CE が Workflow を起動」。

共通の原則：見るは DataSet／AppDB を直読してよいが、書く・守る・記録するは必ず Code Engine を通す（画面は書き換えられる前提 → §2 フロント／バック）。画面が Workflow を直接起動することはなく、通知の起動（と閾値遷移の判定）は CE が握る。起動のたびに CE が最新の有効版を解決するため、Workflow を改版してもカードの再埋め込みは不要。

設計の肝（4 つ）

詳細①：AppDB（アプリ専用の文書 DB）

アプリが所有する NoSQL の JSON 文書ストア。登録してすぐ読む小さな即時 CRUD に向く。DataStore ▸ Collection ▸ Document の 3 階層。

AppDB と DataSet の違い（使い分け）

どちらも「データを置く所」だが役割は逆。AppDB＝書いてすぐ読む小さな記録、DataSet＝集計・可視化する大きな表。

このアプリ：取引（TRANSACTION）・残高（BALANCE）・通知状態（ALERT_STATE）は AppDB（即時 CRUD）、品目×ロケーション残高の集計は DataSet（出力「Inventory Management ｜ Dashboard」）。AppDB は標準同期で DataSet 化され、両者は橋渡しできる。

詳細②：Code Engine（サーバー側の関数）

Pro Code・Workflow・プロンプトから呼ぶサーバー関数。画面は書き換えられる前提とし、守るべき判断（検証・権限・記録）をサーバーに集約する。

詳細③：AI Agent（Workflow 内で自律実行）

知識・道具・指示を与えると自分で手順を踏む AI。知識＝context DataSet／道具＝Code Engine 関数／指示＝プロンプトの 3 点で性格が決まる。

詳細④：通知 Workflow（閾値遷移で人へ知らせる）

通知は画面から直接送らず、別の Workflow に切り出す。Code Engine が閾値の遷移（NORMAL⇄SHORTAGE）を検知し、モデルの有効な最新版を実行時に解決して非同期で起動し、AI Agent が本文を組み立てて 1 通のメールに集約する。画面を待たせず、失敗も局所化できる。

関心の分離

記録（CE）と通知（Workflow）を分ける。片方を直してももう片方に波及しない。

AI が本文を作る

不足明細を読みやすい 1 通へ要約。確定 5 入力（event_type ほか）から組み立てる。

連投を防ぐ

状態（ALERT_STATE＝NORMAL⇄SHORTAGE）を持ち、SHORTAGE の間は再送しない。NORMAL へ戻って再び割れた時だけ送る。

非同期で止めない

通知の勘所：送るのは「閾値をまたいだ瞬間」だけ（NORMAL⇄SHORTAGE 遷移）。連投は ALERT_STATE で防ぎ、起動結果は ALERT_HISTORY に STARTED／FAILED と残す（起動しない場合は SKIPPED。未達も追える）。起動のたびに CE が最新の有効版を解決するため、Workflow を改版してもカードの再埋め込みは不要。重い処理（残高の再計算など）も、同じく CE / Workflow に寄せて画面を止めない。

エージェントの失敗を『見分ける・止める・戻す』

エージェントは自信ありげに間違える。初学者が一番こわいのは「暴走」と「思い込み」。よくある失敗の見分け方と、止め方・戻し方をまとめる。

非常ブレーキ：意図しない動きをしたらまず止める（エージェントの停止ボタン／Esc、ターミナルは Ctrl+C）→ 状況を確認 → 直前の変更を取り消す。取り消し手順は §10「困ったとき」。

安全ガード：本番を守る線引き

エージェントに任せてよい線と、人間が必ず握る線をはっきり分ける。顧客の本番インスタンスでは「承認ゲート型（人が確認してから公開）」を既定にする。

任せる線 ／ 止める線

このアプリで守る具体ガード

名札なしで本番を書き換えない

書込みコマンド（apply／app-studio／workflow／cleanup-legacy）は、名札（INVENTORY_SANDBOX_SUFFIX）が無い＝本番名なら実行前に拒否して即停止する（§7）。これが最大のガード＝人の注意力に頼らず機械が止める（本番メンテナのみ INVENTORY_ALLOW_PRODUCTION=1 で解除）。

design id の扱いで本番を守る

dev-guide-app は配布時に manifest.json の design id を外してある。pro-code 側は本番の id を残したまま配る（自分で外す学習ステップ）ため、自分のコピーでは publish 前に名札付きの sync-manifest が id を外す（または手でキーごと削除）＝初回の domo publish は新規採番（自分専用の design）になり、同じインスタンスへ公開しても本番 design を上書きしない（→ §5・§7）。

本番は名札（INVENTORY_SANDBOX_SUFFIX）で守る

書込みは ① provision_domo.py apply／② app-studio・workflow／③ 画面の入出庫記録・残高再計算（CE 経由）。名札を付ければ自分のサンドボックスに作用し本番・他参加者に触れない。名札なしの ①②（＝本番名）はスクリプトが拒否（本番保護ガード・本番メンテナのみ INVENTORY_ALLOW_PRODUCTION=1）。読み取り専用の verify／sync-manifest／export-app-studio は常に通る。

壊しても取引から作り直せる

残高（BALANCE）は投影なので、おかしくなっても正本の TRANSACTION（追記専用）から RECALCULATE で作り直せる。REGISTER は request_id で冪等＝再送しても二重計上しない。だからサンドボックスで安心して試せる（→ §3）。

名札で名前が分かれる

名札（INVENTORY_SANDBOX_SUFFIX）を付けると App Studio アプリ名だけでなく AppDB・Code Engine・DataFlow・出力 DataSet・通知 Workflow まで全オブジェクト名に「（検証・氏名）」が付き、1 人＝1 セットで本番や他参加者と衝突しない（→ §7）。

secret を残さない

トークン・SID をチャット／コミットに貼らない。git add -A を避け、git add pro-code/app.js のように触ったファイルだけを明示パスで。生のトークンは環境変数か gitignore 済みファイルにだけ置く。

他人の資産に触れない

名札で持ち主が分かる＝「（検証・自分の氏名）」付き以外は編集・削除しない。他人の「（検証・別の氏名）」資産や名札なしの本番資産には手を出さない（確認は読み取り専用の verify で足りる）。

結果を確かめる

「できた」で終えず、実画面・実出力で裏を取ってから次へ。例：verify が ok:true か／PNG 目視／実画面の在庫数・不足件数が意図どおりか。

承認プロンプト＝関門が実際に起きる場所

エージェントはコマンド実行やファイル編集の前に「許可しますか？」と尋ねる。§6・§8でいう「人間が関門を握る」は、この承認プロンプトへの返事で実現する。ここが安全の土台。

Domo MCP と 今回のスキルの使い分け（任意）

Domo MCP は、AI クライアント（Claude Desktop／Claude Code／VS Code など）を Domo につなぐ公式の接続口（MCP＝Model Context Protocol・Anthropic 発のオープン標準）。読み取りが中心だが、別の提供ツール群で作成・管理（書き込み）もできる（2026-10 時点で公開ベータ・つないだ人の Domo 権限の範囲で動く＝代理実行）。今回のスキル（コードを書いて配備）とは競合でなく補完で、このハンズオンは MCP を使わずに完結する（MCP は任意の「調べる相棒」）。違いは下表。

補完の使い方：まず MCP で既存の Domo（スキーマ・サンプル・現状）を調べて文脈を集め、その文脈をもとに今回のスキルでコードを書いて配備する＝〈MCP で調べて → スキルで作って配る〉。在庫での例：MCP で既存の在庫 DataSet の列名（品目コード・ロケーション・現在庫など）を確かめ、その列名のままスキルで表示カードを書く。同じエージェントの会話の中で、調べる（MCP）と作って配る（CLI／REST）を使い分けられる。Anthropic も、エージェントに渡す「手順（スキル）」と「能力（MCP）」は別レイヤーで補完し合うとしている。

使う前に：環境と権限を確認

Domo MCP が自社インスタンスで使えるかは環境依存（公開ベータ・エディション・AI 利用権限・管理者の有効化）。使う前に管理者へ有効化と権限を確認する。使えなくても本ハンズオンは完結する（MCP は不要）。

MCP は Domo 専用ではない

MCP はオープン標準で、Web 検索など他の MCP サーバも同じ仕組みで「エージェントに道具を渡す」。固有のツール名・本数・対応面は実装／版で変わるので、接続後にツール一覧で現行を確認する。Domo 公式の MCP と、GitHub 等の非公式／第三者実装は区別する。
