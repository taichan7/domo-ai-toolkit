# Domoモバイル実機試験ガイド

## 現在の試験状態

| 項目 | 状態 | 根拠 |
|---|---|---|
| 単一レスポンシブ画面 | 静的確認済み | viewport 1件、767px以下の1列レイアウト、固定viewport高を使わない文書フロー |
| PC向け情報密度 | 静的確認済み | 981px以上で余白・パネル・KPIを圧縮、1200px以上で候補を2列化 |
| 横スクロール分離 | 静的確認済み | ページ全体は横方向を抑止し、履歴テーブル内だけ許容 |
| Domoモバイル環境判定 | 実装済み | `domo.env.platform === "mobile"` / mobile flag / Domo UAでホストを判定 |
| 回転・キーボード追従 | 実装済み | `visualViewport`、`resize`、`orientationchange`で実表示高を反映 |
| カメラ起動・背面カメラ優先 | 実装済み | `getUserMedia`, `facingMode: environment` |
| QR検出 | PC／iOS Domo Mobileで実読取確認 | 無関係なはがきQRを両環境で文字列まで検出し、アプリ形式チェックで正常拒否。標準検出が未検出／例外なら同じフレームをjsQRへ渡す |
| 端末カメラ／写真フォールバック | 実装済み | ライブ映像を全端末の既定にし、iOSで全画面化しても読み取りを継続、成功時は`webkitExitFullscreen`で自動復帰。ライブを開始できない端末でだけ`accept="image/*" capture="environment"`を露出。画像は外部送信しない |
| 権限拒否・未対応端末 | 実装済み | 端末カメラ撮影・写真選択・手入力の三段フォールバック |

実機試験を完了したと見なさないこと。`BarcodeDetector` はWebView依存なので、未対応時はクライアント解析へ切り替える。ライブカメラ自体がWebViewで許可されない場合は「カメラで撮影」または「写真から選ぶ」で続行し、それも利用できない場合だけ手入力する。

## レスポンシブ設計の方針

- PCとモバイルでHTMLを分けず、iframeの実幅をCSS media queryで判定する。
- Domo Mobileのホスト判定は、横向きでも下部ナビを維持するなどホスト固有の操作にだけ使う。
- App Studioのcompact layoutは全幅12列・高さ29行、標準は60列・高さ82行とし、終端PAGE_BREAK、`isDynamic: false`、`fitToFrame: false`、カード操作は既定（未設定＝操作許可、`editInAppViewer: true`）とする。Domo Mobile内ではiframeを実ビューポート（`100dvh`）へ固定し、`.app-shell`をその高さに収めて`main`だけを縦スクロールさせる。
- PCは見出し・余白・カード高を詰めて業務情報を一覧しやすくする。モバイルは44px以上の主要タッチ領域と1列操作を優先する。
- グラフはCanvasライブラリではなくCSSとDOM要素で描画しているため、幅変更時はブラウザの再レイアウトで追従する。固定ピクセル幅や縮小transformは使わない。
- ノッチはsafe-area、ソフトウェアキーボードと回転は`visualViewport.height`を使ってモーダルの最大高へ反映する。

### 同僚資料との対応

添付の「Domo ProCode モバイル表示対応手順書」（2026-08-08、18ページ）から、viewport、iframe実幅に基づくmedia query、固定幅／`min-width`／絶対配置の抑制、`transform: scale()`不使用、グラフ親領域のレスポンシブ化、実機確認を採用した。`domo.env.platform`はDomo Mobile固有のナビ動作にだけ使い、主レイアウトは画面幅で決める。Manifest metadataだけにレスポンシブを依存しない。

## PC／画面幅別チェック

| 区分 | 基準サイズ | 主な期待結果 |
|---|---:|---|
| PC Web | 1440 × 900 | 5列KPI、2列ダッシュボード、コンパクトなサイドバーとパネル |
| タブレット縦 | 768 × 1024 | 省スペースサイドバー、2列KPI、1列ダッシュボード |
| モバイル縦 | 390 × 844 | App Studio内上部ナビ、iframe文書スクロール、1列操作、2列以下のKPI、ページ横スクロールなし |
| モバイル横 | 844 × 390 | Domo Mobileでは上部ナビを維持し、本文、モーダル、候補一覧をスクロールして到達できる |
| 小型モバイル | 375 × 667 | 主要操作44px以上、テーブル以外の横スクロールなし |

ブラウザの開発者ツールでは各サイズで`document.body.scrollWidth <= window.innerWidth`を確認する。履歴テーブルを横へ動かした場合も、ページ本体とヘッダーが一緒に移動しないことを確認する。

## 準備

1. iOSとAndroidのDomoモバイルアプリを最新化する。
2. `maintenance-instance.domo.com` へ検証用Domoユーザーでログインする。
3. App Studioの「在庫入出庫管理ハンズオン」をモバイルで開く。
4. 画面が表示されること（ヘッダーと上部タブ「入出庫／分析／履歴」が出ること）を確認する。「起動に時間がかかっています」または「アプリを起動できません」が出た場合は、その文面を記録する。挙動が古いと感じる場合はDomo Mobileを完全終了して再起動し、最新バンドルを取得する。
5. QRを読む端末とは別に、`LOC:LOC-01` と `ITEM:ITEM-001` を印字したQR（ロケーション／品目コードに対応）を紙またはもう一台の画面へ用意する。

## iOS／Android共通チェック

### 起動とレイアウト

- 縦向きでヘッダー、入出庫フォーム、アプリ内ナビが重ならない。
- 横向きへ回転しても、Domo Mobileではサイドバーに切り替わらず上部ナビを維持する。
- 見出しの下から本文を縦へスワイプし、ロケーション候補、品目候補、数量、確認ボタンまで到達できる。
- ボタンと数量コントロールを片手で操作できる。
- 文字やテーブルがページ全体を横スクロールさせない。履歴テーブル内の横スクロールは許容する。
- ノッチ、ホームインジケーター、キーボード表示時に重要操作が隠れない。
- QRモーダルを開いたままキーボード表示・回転を行い、閉じるボタンと手入力欄へ到達できる。
- 画面内を一度タップしても青いカード枠に固定されず、続けて入出庫、分析、履歴を順に操作できる。

### QRとカメラ

1. 「QRを読む」を押し、カメラを許可する。
2. STEP 1の読取りで `LOC:LOC-01` を使い、「中央倉庫 / LOC-01」が選択される。
3. STEP 2の読取りで `ITEM:ITEM-001` を使い、「安全手袋 / ITEM-001」が選択される。
4. STEP 1で品目QRを選び、「品目QRを読み取りました。現在はロケーション選択です」と検出成功と手順が区別される。
5. iOSではライブ映像が全画面化されることがあるが、そのままQRを枠に合わせると読み取り、成功時に全画面を抜けてアプリ画面へ自動で戻る。
6. 読み取り前に全画面を閉じた場合は［ライブ映像を再開］が表示され、押すとライブ映像が再開する。
7. カメラ権限を拒否した場合、または非セキュアな画面でだけ「カメラで撮影」と「写真から選ぶ」が表示され、同じQRが選択される。
8. はがきやURLなど無関係なQRを読み、「QRコードは読み取れましたが、このアプリ用ではありません」と区別して拒否される。
9. `https://invalid.example` のような値を手入力し、Pro Codeの形式判定で拒否される。
10. 端末設定でライブカメラ権限を拒否し、端末カメラ撮影・写真選択・手入力で作業を継続できる。

### 登録

- 入庫1件を登録し、完了トーストとAppDBから読み直した現在庫を確認する。
- 出庫数が現在庫を超えると、UIとCode Engineの両方で登録できない。
- 登録ボタンを2回押す、または通信中に再送し、同じ `request_id` の取引が1件になる。
- 一般ユーザーに管理画面が表示されない。

### 通信エラー

1. QRと入力を完了させ、端末を一時的に機内モードにする。
2. 登録を実行し、ローディング後に内部情報やトークンを含まないエラーと再試行案内が出る。
3. オンラインに戻し、同じ確認画面から再実行できる。
