Domo の開発は、ブラウザのクリックではなく VS Code ＋ コーディングエージェント ＋ Domo CLI で行える。コードを手元で書き、ローカルで確かめ、CLI/API で Domo へデプロイする。本書は、環境を 6 つ整えるところから、開発モデル・このアプリの構造・作れるものの全体像・デプロイの仕組み・エージェントの回し方までを図と表で辿る。最後に各自のコピーを作って「編集 → 公開 → 確認」を 1 周する。本番を壊さないための安全の線引きも合わせて示す。

事前課題（当日までに・15〜30 分）

当日の朝に慌てないよう、家で「緑」にしておく

「緑」＝準備 OK（信号の緑＝進んでよい）の状態。下の項目がすべて済めば緑で、これは §1 末尾のやってみよう①（6 つの点検）を家で先に済ませておくもの。

はじめに確認：当日使う端末にソフトを入れられるか（会社管理 PC は winget や npm install -g が禁止のことがある）。入れられないときは、事前に情シスへ申請するか、貸与端末・管理者権限ターミナルを手配する（迷ったら運営へ）。

  1. 公開toolkitをcloneし、reference-architectures/ 内のpl-summary-app フォルダを分かる場所に置く（§1「そろえる 6 つ」STEP 1）。
  2. VS Code とエージェント拡張を入れて、サインインできる（§1「VS Code を入れて、フォルダを開く」「エージェント拡張を入れる」）。
  3. Node・Python・Git・Domo CLI を入れて、domo login まで通す（§1「Node・Python・Git を入れる」「Domo CLI を入れて、ログインする」）。
  4. domo-ai-toolkit を clone して、疎通スクリプトが通る（§1「土台を置く」）。
  5. domo login -i your-company.domo.com（ブラウザ SSO）まで通す。データ層・Pro Code・App Studio 埋め込みはこのログインだけで動く＝トークン不要。開発者トークンはワークフロー層（AI 長文レポート）だけに要る任意で、使う回のみ §1「②の認証を整える」で発行（管理者権限が要る・無ければ運営へ）。
  6. domo dev で Pro Code のローカルプレビューがブラウザで開けることを確認（任意・domo login だけで動く）。
  7. （任意・人数が多い回は推奨）~/handson-pl へコピー → pro-code/manifest.json の id を外す → domo publish まで済ませる（§7）。

撤退ライン：どこまで粘るか

自分で直す＝打ち間違い・パス・環境変数・ログインのやり直し。撤退＝社内プロキシ／SSO／証明書エラー、管理 PC のインストール禁止、トークン発行に要る管理者権限が無い。設定を変えても同じエラーが出るなら環境・権限側で、自分では直せない合図。目安 15 分で糸口が無ければ、自社の情シス／Domo 管理者（当日は運営）へ回す。

OS 別の落とし穴（詰まりやすい 3 点）

導入そのものより、導入のあと「版が出ない／.sh が動かない」でつまずくことが多い。自分の OS の 1 枚を先に読んでおくと、同じ所で止まらずに済む。

macOS：PATH と初回起動

Apple Silicon の Homebrew は /opt/homebrew/bin に入る。brew install 後に node --version が出ないときは、案内に出る eval "$(/opt/homebrew/bin/brew shellenv)" を実行してターミナルを開き直す。アプリ初回起動で「開発元を確認できない」が出たら システム設定 → プライバシーとセキュリティから許可。

Windows：実行ポリシー

PowerShell で npm／domo が「スクリプトの実行が無効」で弾かれたら、PowerShell で Set-ExecutionPolicy -Scope CurrentUser RemoteSigned を一度だけ実行。winget 導入後に版が出ないときはターミナルを開き直す（PATH 再読込）。

Git Bash：改行（CRLF）

配布キットの .sh（starter の examples）が Windows の改行で保存されると \r 混入で失敗する。git config --global core.autocrlf input を設定し、.sh は LF のまま扱う。コマンドが途中で切れる・引数が崩れるときは改行コードを疑う。

ネットワークで詰まったら（プロキシ・証明書・SSO）

社内ネットワークでは、ツール自体は正しくても通信の途中で弾かれて止まることがある。多くは下の 3 パターン。自分で設定を変えても同じエラーなら「環境・権限側の壁」＝粘らず情シス／運営へ（下の事前課題の撤退ライン・目安 15 分）。

プロキシ（npm が固まる・タイムアウト）

社内プロキシ経由だと npm install -g ryuu や git clone が進まない。会社のプロキシ URL を HTTPS_PROXY／HTTP_PROXY 環境変数（と npm の設定）に入れると通ることが多い。値は情シス支給のものを使う。

証明書（SSL／self-signed）

SELF_SIGNED_CERT_IN_CHAIN／unable to get local issuer certificate は、社内の検査プロキシが独自 CA 証明書を挟んでいる兆候。検証を切る（NODE_TLS_REJECT_UNAUTHORIZED=0）のではなく、会社の CA 証明書を NODE_EXTRA_CA_CERTS／git config http.sslCAInfo に登録するのが正しい直し方。

SSO（ログイン画面が開かない）

domo login はブラウザを開いて SSO 認証する。ポップアップブロックや既定ブラウザ未設定で画面が出ないことがある。手動で既定ブラウザを開いてから再実行し、会社の IdP（SAML／OAuth）でサインインする。通ったあと ryuu が認証を保持する。

切り分けのコツ

「ツールが無い」のか「通信が弾かれる」のかで対処が分かれる。版は出るのに clone／login／install だけ失敗するなら、ネットワーク側を疑う。下のコマンドで現在の設定と到達性を確かめられる。

権限とトークン（デプロイの前提）

管理者権限で行う

アプリ作成・カード埋め込みができる権限が要る（データフロー実行は本ハンズオンでは不要・一般開発では必要）。無い場合は管理者に依頼する。

認証は 2 系統ある

① domo コマンド（publish 等）＋データ層スクリプト provision_domo.py（apply／sync-manifest／app-studio／verify）＝domo login（SSO）で動く（トークン不要）。② ワークフロー層 provision_workflows.py（AI 長文レポート）だけ＝開発者トークン＋DOMO_INSTANCE（または SID）が必須（configstore を読まない面だから）。ここが唯一のつまずき。

トークンは貼らない

チャット・コミットに残さない。CLI 設定領域か gitignore 済みファイルにだけ置く。

domo login と 開発者トークンの違い（認証の 2 系統）

domo login は既定でブラウザ SSO（シングルサインオン）（方式は会社の IdP による）で、データ層スクリプト（provision_domo.py）と domo publish はこのログイン情報（configstore）だけで動く＝トークン不要。一方ワークフロー層（provision_workflows.py）だけは configstore を読まず、開発者トークン（または SID）＋インスタンス名を環境変数から読む。どちらも「あなたの権限」で動く。本当の違いは《使う道具》と《資格情報の寿命》の 2 軸だけで、「片方でしかできない」は“能力の壁”ではなく“どの道具がどの面に届くか”（下の表＝しくみ／その下の 2 枚＝担当範囲）。

一方だけでできること（担当範囲）

下の 2 枚が各道具の担当範囲。SSO（domo login）で届く面が広いのがこのアプリの特徴＝Pro Code の公開もデータ層の配備も App Studio 埋め込みも SSO だけでできる。REST（開発者トークン）が要るのはワークフロー層（AI 長文レポート）だけ。右の「できない」の多くは“能力の壁”ではなく道具の都合（ワークフロー層スクリプトが configstore を読まない）。

「トークンは正しいのに動かない」

文字列を疑う前にエラー番号で切り分ける。
401＝トークン未設定／無効／インスタンス不一致（発行先＝DOMO_INSTANCE が一致するか確認）。
403＝認証は通ったが権限不足（App Studio 作成・埋め込みの権限が要る）。

「開発者トークン」の取り違え

フロントエンド と バックエンド（責務の分担）

「どこで開発するか（外／内）」とは別に、動くもの自体も フロントエンド（画面） と バックエンド（サーバー・データ） に分かれる。画面は信用しすぎない――守る判断と重い処理はバックエンドに置くのが要。

この分担がこのアプリの背骨：フロント（Pro Code）＝表示、バック（CE／ETL／Workflow／AppDB）＝守る・計算・保存。中身は §3 で分解する。

「生成」と「表示」を分ける＝このアプリの要の設計。長文 AI レポートは見るたびに作らない。Workflow（WF-01）が実行時に全店舗を回し（店舗ループは「15 秒待機」で同時実行を平準化）、統合サブWF の AI が書いた結果を pl_report_api(save) で AppDB に溜める。フロントは AppDB を読むだけなので瞬時に出る。約 100 店舗ぶんのディスパッチにおよそ 25 分かかるが、それはデモ前に一度流せばよい（表示側は待たされない）。

作る＝Domo の外（手元のファイル・エージェント・CLI）、動く＝Domo の中（実行時）。外のファイルが真実の源。
フロント / バック
フロント＝画面（Pro-Code）。バック＝サーバー・データ（CE／ETL／Workflow／AppDB）。守る判断と重い処理はバックへ。
生成と表示の分離
重い AI 生成は Workflow で事前に行い AppDB へ保存。表示は保存済みを読むだけ＝待たせない。
状態機械
段階を順に進める仕組み。WF-01 は店舗ループと全社ブランチが並列に走り、終了ノードは 2 つ。

PL_SANDBOX_SUFFIX で作る自分専用スタック。本番へは PL_ALLOW_PRODUCTION を立てたときだけ出る。

4 面の AI サマリーを食い違わせない（状態ラベルの一元化）

状態ラベル＝ETL の決定的列（単一の真実）。店舗の状態ラベル（好調≥8%／堅調 5-8%／要注意 0-5%／回復基調＝利益率<0 かつ前月比利益改善／不振）は SQL CASE で機械確定し 状態ラベル 列として出す。短文タイルも長文エージェントもこの列を再判定せず一字一句転記する。短文は domogpt-medium、長文は Claude 系と別モデルのため、境界判定（赤字だが改善は「回復基調」か「不振」か等）を各 LLM に委ねると食い違う。判定を列へ寄せ両者を転記に徹させることで構造的に一致を担保する（全社は集計値のため 4 値）。

状態ラベルの境界ケース（迷いやすい 2 本の線）

現場で判定が割れるのは赤字の内側。利益率が負の店舗を「回復基調」と「不振」に分けるのは前月比利益変化率の符号だけで、赤字の深さや改善幅の大きさは関係しない。だからこそ ETL の CASE に寄せ、AI には判定させない。

店舗は 5 値・全社は 4 値。全社は集計値のため「回復基調」を持たず、全社赤字はすべて「不振」になる。もう 1 本の迷いやすい線が0% 境界＝利益率ちょうど 0.0% は「要注意」（0 以上 5% 未満）側に入る。「黒字／赤字」は状態ラベルとして使わない（補足説明では可）。閾値を変えるときは SQL の CASE・共通規約・各プロンプトの注記を同時に直す。

AI は 2 系統を使い分ける（短文 ↔ 長文）

画面のサマリータブは AppDB を content.store_id（全社は "ALL"）でクエリし、generated_at 降順の最新 1 件の analysis_html を描画する。急な店舗切替でも state.reqSeq トークンで応答の順序逆転による誤表示を防ぐ。AI 本文が未生成の店舗は「準備中」フォールバックを出し、AI 生成と偽らない。短文（概要タブ）は summary の 店舗別AIサマリー／全社AIサマリー 列を直読する。

全社短文は「行ごと実行」のバリアントを決定的にまとめる。全社AIサマリー 列は DataFlow の TextGeneration が行ごとに走るため、同じ全社入力でも僅かに文面の違う複数バリアントが混在しうる（いずれも全社視点で等価）。画面は最頻値を決定的に選ぶことで、どの行から読んでも同じ全社短文になるようにしている（表示のブレ止め）。

WF-01 → 統合サブWF へは report_type（store／company）と識別子を渡す。両ブランチの AI はcontext＝summary＋detailを読み、状態ラベルは再判定せず転記、計算させず解釈だけを担う。全社ブランチは純利益ワーストの視点で問題店舗を論じ、予算差異は全社集計としてのみ言及する（店舗ランキングには使わない）。

サマリータブ：最新版の選び方と「準備中」フォールバック

長文レポートは AppDB に何版も積み上がる（WF-01 を回すたびに追加される）。画面は常に最新の 1 件だけを選んで出す。まだ作られていない店舗を「空白」や「古い別店舗の残り」で埋めないための手順がこれ。

doc_key の形＝{store_id}-{period}-{scenario}（全社は ALL-…）。保存CE は同一 doc_key の厳密に古い旧版だけを削除するので、別店舗・別期間のレポートは巻き添えにならない。generated_at が空や ISO8601 不正なら保存時に現在時刻（UTC）へ正規化してから保存する（画面の日時降順ソートに不正値を流さないため）。

詳細①：AppDB（アプリ専用の文書 DB）

アプリが所有する NoSQL の JSON 文書ストア。登録してすぐ読む小さな即時 CRUD に向く。DataStore ▸ Collection ▸ Document の 3 階層。

AppDB と DataSet の違い（使い分け）

どちらも「データを置く所」だが役割は逆。AppDB＝書いてすぐ読む小さな記録、DataSet＝集計・可視化する大きな表。

Magic ETL v2 は draft/version/release が無く「その場編集」（GET→PUT）＝PUT した瞬間に本番。だから TextGeneration のプロンプトだけは deploy_dataflow_prompt.py で安全に差し替える（backup→対象タイルの instructions のみ→PUT→round-trip 厳密検証、RUN=1 で AI 列の再生成までトリガー）。Python タイル・タイル構成は Domo の ETL 画面で編集し、変更後は dataflow 2042 を再実行して summary/detail を作り直す。

関心の分離

再利用できる

失敗の局所化

非同期（wait:False）＋保存CE の per-save 重複除去で、1 件の失敗が全体を止めない。

規模の現実：約 100 店舗 × 15 秒 ≈ 25 分がディスパッチ所要（デモ前の一回限りの populate）。店舗が 100 なら間隔は短くてもよいが、同じ「15 秒間隔＋親子分離」パターンは店舗数が増えるほど効く——AI の同時負荷とクレジットを平準化し、1 件の失敗を局所化するので、数千店舗規模でもメイン＝投入制御／サブ＝1 件生成の役割分担がそのままスケールする。短文サマリー・トレンド・事業部別は DataFlow が全店舗ぶんをまとめて作る分担。

Workflow の 2 つのタイマーと手動トリガー

自動化を「どのペースで・どう起動するか」も設計の一部。このアプリには待機タイマーが 2 枚あり、起動は手動メッセージで行える。

WF-01：15 秒待機

店舗ループに置く「同時実行数を平準化」タイマー。非同期投入のペースを抑え、AI 書込みの取りこぼし（従来実測 10〜15%）を減らす。間隔は PL_PARENT_INTERVAL_SECONDS で調整可。

統合サブWF：5 秒待機

サブWF の先頭に置く「AI 負荷平準化」タイマー。1 件あたりの処理が AI サービスへ一斉に当たらないようにする。

手動起動は instances/message エンドポイントに messageName="manual" と modelId を POST する（検証済み。/status サフィックスや v2 は 403/404 になるので使わない）。保存CE が per-save で古い版だけ消すので、取りこぼしても前回分が残り画面表示は途切れない＝「2 回連続実行」は必須ではなく、確実な全再生成を期すときだけの安全網。

コードは自動追従

FOLLOW_LATEST。domo publish し直せば、埋め込み済みカードが新しいコードを自動で映す。

データ紐付けは手動

alias（summary／detail／trend／dept）を増減した時だけ provision_domo.py app-studio を再実行して context mapping を同期する。

列追加だけなら不要

なぜ再マッピングが要るのか。pro-code/manifest.json に alias を増やしても、既に埋め込んだカードの context は自動では追随しない（domo publish は "Mapping has changed" と警告するだけ）。未マッピングの alias は proxy で 400（DA0004）になり、FE はトレンド空表示・事業部タブ非表示へ graceful degrade する。app-studio がこの context mapping を PUT で揃える（回帰ガードは tests/test_provision_domo.py）。

3 タブと供給源（どの段が、どのタブを満たすか）

Pro Code カードは 概要・事業部別・サマリーの 3 タブ。概要／事業部別（KPI・チャート・ETL 短文 AI サマリー）はデータ層＝apply が作る DataFlow の 4 出力（summary／detail／trend／dept・2 枚の TextGeneration タイルが店舗／全社の短文を出力）だけで動く。サマリータブ（経営インサイトの長文 HTML）はワークフロー層が AppDB の analysis_html を書くまで「準備中」フォールバックになる。だから画面だけの実習なら配備 1・2 で完結し、長文 AI は任意。

名札（サンドボックス）と本番ガード

provision --apply には門番がある。AppDB コレクションと summary データセットが見つからなければ明示的に失敗する（保守用インスタンスの GUID を顧客環境へ焼き込まないため）。だから必ずデータ層（apply・sync-manifest）を先に通すこと。なお保守／移行用の ce／subflow／mainflow／delete-wf03 は固定の本番モデル ID 対象でサンドボックスでは隔離できない＝名札運用では provision を使う。

ワークフロー層（任意・長文 AI レポート）

長文 AI は 3 資産からなるワークフロー層が生む。保存CE（pl_report_api・save は保存＋同一 doc_key の旧版削除を内包）、統合サブWF（開始→待機→report_type ゲートウェイ→店舗 AI／全社 AI→保存。全社ブランチは Send Email も保持）、メイン WF-01（並列サイドブランチ＋終了 2 つ・店舗ループは 15 秒待機を挟む）。provision --apply --release がこれらを名称で発見／新規作成し、束縛を対象環境の実 ID へ張り替えて release する。メール宛先だけ env PL_EMAIL_PERSON_RECIPIENTS で渡す（焼き込まない）。

sync-manifest
apply が確定した実 ID を pro-code/manifest.json の alias→dataSetId／コレクション id へ冪等に書き込む。publish より前に走らせる。

エージェント駆動の開発ループと規律：小さく回し、関門は人が握る

仕様を一度に固めず、小さく作って手元で確かめ、公開して確認する。この 1 周をエージェントとの対話で速く回す。賢さより「正しい文脈を渡すこと」と「関門を人間が握ること」が成果を決める。

1 変更＝1 周（赤いタイルは人間が握る関門）

なぜ「小さく」なのか。 1 周を小さく保つと、崩れたときに原因が最後の 1 変更に絞れる。pl は pro-code（画面）・dataflow（集計）・workflow／code-engine（AI 生成と保存）と層が分かれるので、層をまたぐ変更ほど小さく刻む。「1 文で説明できない変更」は分割の合図。

「正しい文脈を渡す」＝ 作業に必要な資料だけを指す

エージェントに全部読ませない。規約（AGENT.md）＋その作業に要る資料だけを渡すと、賢さに関係なく作法どおり動く。やりたいことから渡す資料が決まる。

AI が触る『契約』は不変。 pl のバックエンドは、公開関数 pl_report_api・データセット別名 summary／detail／trend／dept・レポート種別 report_type（店舗／全社）・保存キー doc_key という固定の約束の上で動く。エージェントに改名・別経路を提案されても、この契約には触らせないのが文脈設計の芯。

頼み方の良し悪し（Before / After）

同じ「お願い」でも、書き方で成果が段違い。悪い例と良い例を見比べると、本書各所のコピーして使えるプロンプトがなぜ良いのかが分かる。

仕上げる前に、エージェントとレビューを往復する

一発で完成を狙わない。変更の要点・影響範囲・自信のないところをエージェントに言わせ、人が是非を決めてから次へ進む。往復のたびに差分を小さく保てば、見逃しも手戻りも減る。

①要点を言わせる

「何を・どのファイルで変えたか」を 3 行で。長い自慢話でなく差分の地図を求める。

②弱点を白状させる

「自信のない箇所・未確認の前提」を挙げさせる。そこが次に人が検証する点になる。

③是非は人が決める

直し続けさせず、人が OK／要修正を宣言。公開の承認はこの往復の外（人間の関門）に置く。

レビューを往復するプロンプト（何度でもコピー） 
いまの変更を publish する前にレビューしたい。次の3点だけ簡潔に答えて:
1. 何を・どのファイルで変えたか（要点を3行で）
2. 自信のない箇所・未確認の前提（あれば）
3. 私が実画面で見るべき確認ポイント
その上で node --check pro-code/app.js と node tests/test_drill_helpers.js の結果も教えて。
publish はまだしない（私が「publish して」と言ってから実行してください）。

コーディングエージェントと働く『心得』（一般ガイドライン）

VS Code × コーディングエージェントで Domo を開発するときに、面や言語を問わず効く注意点。賢いモデルでもこの心得を外すと事故る。

エージェントの失敗を『見分ける・止める・戻す』

エージェントは自信ありげに間違える。初学者が一番こわいのは「暴走」と「思い込み」。よくある失敗の見分け方と、止め方・戻し方をまとめる。

非常ブレーキ：意図しない動きをしたらまず止める（エージェントの停止ボタン／Esc、ターミナルは Ctrl+C）→ 状況を確認 → 直前の変更を取り消す。取り消し手順は §10「困ったとき」。

いちばん大事な一線：「できた」で終わらせない。検証（テスト・目視）と公開の承認は、エージェントではなく人間が握る。本番への publish は必ず人が確認してから（→ §8）。

ハンズオン実習：自分のサンドボックスを作って回す

ここが本番。各自の「サンドボックス」（＝自分専用の隔離コピー）を作り、エージェントに小さな変更を頼み、ローカルで確かめ、公開して、ブラウザで反映を確認する。1 周を体で覚えるのが狙い。サンドボックスは本番にも他の参加者にも触れないので、安心して何度でも試せる（しくみは下の囲み）。

名札で分かれるのは「名前」だけ。「AI クレジットの消費枠」は分かれない。名札は本番・他参加者とオブジェクト名を分けるが、同じインスタンスの AI／クレジット枠は全員で共有する。だから DataFlow の実行や WF-01 の手動実行（AI 生成を回す工程）は、名札付きでもそのインスタンスの枠を消費する＝軽い FE 編集ループと違って回数・規模に注意（コストの詳細は後述の注記）。

所要 約 30 分（初回はコピー作成＋publish＋埋め込みで 5〜10 分／2 周目以降は domo publish とブラウザ更新だけ）。やること＝下の図の 6 ステップ（コピー → id を外す → 編集 → ローカル確認 → publish → 反映確認）。

再開時チェック（休憩後・ターミナルを開き直したら必ず）：①domo login -i your-company.domo.com（SID は約 1 時間で失効）②名札 PL_SANDBOX_SUFFIX を再 export（ターミナルを閉じると消える）。AI 長文レポートまで回す回は、あわせて config/secrets.env の開発者トークンを読み込む（§1「②の認証を整える」）。これらを先に済ませてから apply／publish／埋め込みへ。

Domo MCP と 今回のスキルの使い分け（任意）

Domo MCP は、AI クライアント（Claude Desktop／Claude Code／VS Code など）を Domo につなぐ公式の接続口（MCP＝Model Context Protocol・Anthropic 発のオープン標準）。読み取りが中心だが、別の提供ツール群で作成・管理（書き込み）もできる（2026-10 時点で公開ベータ・つないだ人の Domo 権限の範囲で動く＝代理実行）。今回のスキル（コードを書いて配備）とは競合でなく補完で、このハンズオンは MCP を使わずに完結する（MCP は任意の「調べる相棒」）。違いは下表。

補完の使い方：まず MCP で既存の Domo（スキーマ・サンプル・現状）を調べて文脈を集め、その文脈をもとに今回のスキルでコードを書いて配備する＝〈MCP で調べて → スキルで作って配る〉。同じエージェントの会話の中で、調べる（MCP）と作って配る（CLI／REST）を使い分けられる。Anthropic も、エージェントに渡す「手順（スキル）」と「能力（MCP）」は別レイヤーで補完し合うとしている。

MCP で「調べる」具体例

このアプリに重ねるなら：summary／detail の列構成やサンプル行を会話で確認する／店舗別損益AI要約 コレクションにどんな doc_key が入っているかを眺める／似た既存カードを横断検索して作り方の下敷きにする。いずれも読み取りだけで、文脈集めに向く。

スキルで「作って配る」具体例

集めた文脈をもとに：集計 SQL に派生列を足す／prompts/ の指示文を磨く／pro-code/ に表示を 1 つ加える → ローカル検証 → publish／API で配備。残したい資産はこちら（コードとして版管理）で作る。

使う前に：環境と権限を確認

Domo MCP が自社インスタンスで使えるかは環境依存（公開ベータ・エディション・AI 利用権限・管理者の有効化）。使う前に管理者へ有効化と権限を確認する。使えなくても本ハンズオンは完結する（MCP は不要）。

MCP は Domo 専用ではない

MCP はオープン標準で、Web 検索など他の MCP サーバも同じ仕組みで「エージェントに道具を渡す」。固有のツール名・本数・対応面は実装／版で変わるので、接続後にツール一覧で現行を確認する。Domo 公式の MCP と、GitHub 等の非公式／第三者実装は区別する。
