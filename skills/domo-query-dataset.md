# Domo Query Dataset

Operating notes for the **Domo "Query Dataset API"** — a tiny **single-operation** surface that runs a caller-supplied SQL string against one DataSet and returns the result as a **JSON object envelope** `{datasource, columns, metadata, numColumns, rows, numRows}` (`POST /api/query/v1/execute/export/{datasetId}`). Read this before touching any `/api/query/v1/execute/export/{id}` call, any code mentioning `QueryDatasetRequest` / `QueryDatasetResponse`, or any "query a dataset with SQL and download the rows" flow — **and especially before assuming this path is the same as, or behaves like, the bare `/api/query/v1/execute/{id}`** (a DIFFERENT, `domo-datasets.md`-owned path — see naming traps). Despite the word **`export`** in the path and an `includeHeader` query param, the documented response is **`application/json`, NOT CSV**. It reads a DataSet's **live rows** and emits them off-platform — treat every call as a **data-egress read** (see Safety & hygiene).

- **Defers**: the **bare** DataSet-SQL query `POST /api/query/v1/execute/{datasetId}` (NO `/export/` segment, request `QueryRequest{sql}`, the `[REPO]` path exercised by `../scripts/query-dataset.sh` + ~59 repo callers) → `domo-datasets.md` — a DISTINCT published path in a DISTINCT spec (`data-sets.yaml`), the sharpest false friend (see naming traps). The **async Export-to-S3 push** `POST /api/query/v1/export/{id}` (rank-20, AWS-creds body, S3 egress) → `domo-export-to-s3.md`. **Beast Mode** (`/api/query/v1/functions`) and **Federated migration** (`/api/query/migration/...`, rank-16) → `domo-beast-mode.md` / `domo-federated.md`. ## The surface, in one line

A **doc-convergent single-world thin island on the STRONG (byte-identical SHA-256) rung** (1 path `/api/query/v1/execute/export/{datasetId}`, 1 op POST with no operationId, 1 host `{instance}.domo.com`, 1 auth `X-DOMO-Developer-Token`) that runs a REQUIRED `{sql}` string against one DataSet and returns a JSON object envelope `{datasource, columns, metadata, numColumns, rows, numRows}` — **NOT CSV**, despite the `export` path segment and the `includeHeader` param. Its defining tension is **spec-distinct-but-backend-opaque**: it is a SEPARATELY-PUBLISHED path from the bare `/api/query/v1/execute/{datasetId}` (distinct file / tag / request-schema name / catalog line — all `[DOC]`), but WHETHER it is a genuinely distinct backend operation or a routing alias of the bare sibling is **UNVERIFIED `[INFER]`**; and the response's `columns` / `metadata` / `rows` are each declared `items:{}` (an EMPTY item schema), so element shapes and any positional alignment are entirely UNSPECIFIED. The candidate is **byte-identical (SHA-256 hash match) to Domo's published spec** with two consistent dev-portal renders (a STRONG convergent pair, like rank-21) — but only **1 verdict earned CONFIRMED** (JSON-not-CSV), because the six most-tempting claims about a thin spec (distinct-op-vs-alias, object-vs-array-runtime, FROM-dialect, `includeHeader`-effect, auth-exclusivity, error-completeness) all over-claim. **Zero repo callers of `/execute/export/`** (`grep 'execute/export'` = zero; every `/execute/` caller is the BARE sibling) → all runtime/response/error behavior is `[DOC]`/`[INFER]`-never-`[REPO]`, 0 executed calls.

## Schemas (shapes `[DOC]`; the untyped items + response-shape tension are the story)

- **`DatasetIdParam`** — `type: string`, description `"<DATASET_ID>"`. REQUIRED as the `{datasetId}` path param (the op re-declares it "The dataset identifier."). NO `format` → an opaque id string `[DOC]`.
- **`QueryDatasetRequest`** (REQUIRED body) — `type: object`, exactly ONE property `sql` (`type: string`), listed as `required`. It is the ONLY request field — no `limit`, `offset`, `format`, or body-level `includeHeader` `[DOC]`. The `sql` field carries NO description; the only hint at its content is the schema `example` `SELECT * FROM \`<DATASET_ID>\` WHERE status='error'`. The backtick-quoted dataset id in that example is **illustration, not a documented grammar** — the dataset resolves from the `{datasetId}` PATH, and `FROM your_table` (the bare sibling's example) / `FROM table` (the repo script) are equally valid forms; asserting a required SQL dialect, quoting rule, supported clause/function set, or row cap over-claims (`[INFER]`, Do-NOT #3).
- **`QueryDatasetResponse`** (200 body) — `type: object` (an ENVELOPE, not a bare array) with exactly SIX properties: `datasource` (string), `columns` (`array`, `items: {}`), `metadata` (`array`, `items: {}`), `numColumns` (integer), `rows` (`array`, `items: {}`), `numRows` (integer). **`columns`, `metadata`, and `rows` are each `items: {}` — an EMPTY item schema that permits any JSON and specifies NOTHING about element structure**: the shapes of `columns[i]` / `metadata[i]` / `rows[i]`, and any positional alignment between `columns` and `rows`, are entirely UNSPECIFIED (`[INFER]`, Do-NOT #7). The worked example shows `datasource:"<DATASET_ID>"`, `columns:[]`, `metadata:[]`, `numColumns:10`, `rows:[]`, `numRows:15` — note `numColumns:10` with an EMPTY `columns` array and `numRows:15` with an EMPTY `rows` array, so the example does NOT establish `numColumns==len(columns)` or `numRows==len(rows)` (Do-NOT #8). `datasource` ("the queried id echoed back") and `metadata` (no description, untyped, empty in the example) have no documented semantics beyond their types (`[INFER]`). The schema `description` ("Description of the Response with an example of the data") and the `includeHeader` param description ("includeHeader") are placeholder/self-referential — read no field semantics from them.

The **documented** difference from the bare sibling (`data-sets.yaml`'s `QueryResponse`, a top-level `array` of flat row-objects) is real `[DOC]` — but the bare path's own `[REPO]` code parses an OBJECT, so do not elevate the object-vs-array difference to a RUNTIME invariant (Do-NOT #2). The envelope matches Domo's documented OAuth query-endpoint family shape (`datasource`/`columns`/`metadata`/`rows`/`numRows`/`numColumns`, minus `fromcache`), so the fields are a genuine Domo response shape, not invented `[DOC]`.

## Safety & hygiene

- **Data-egress READ — not destructive, but not free.** rank-23 does NOT create, mutate, or delete anything on the platform: it runs a caller-supplied `SELECT` and returns rows. So — like rank-22 (Get KPI Card Image) and unlike the two destructive surfaces (rank-20 Export-to-S3 hands out raw AWS creds; rank-21 Dataset History DELETE is irreversible) — this surface is **ELIGIBLE for autonomous, documentation-only work**. **But any LIVE call reads a DataSet's live rows and emits them off-platform** (into a response body, a log, a file, a downstream system). Treat the SQL as arbitrary and the output as sensitive: a `SELECT *` can egress PII / financial / customer data. Scope queries to the columns actually needed; never widen a query, tee its output to a shared location, or persist returned rows without an explicit, current instruction from the human. This skill's own verification executed **ZERO** HTTP calls — keep it that way unless the human explicitly asks for a live query against a named dataset.
- **Opaque-contract footguns.** The response `columns`/`metadata`/`rows` are `items:{}` (untyped) and the example's counts (`numColumns:10`/`numRows:15`) do not match its empty arrays — so any code consuming this endpoint must **read the actual runtime body**, not the spec's element shapes or the bare-sibling's shape, and must not assume `numRows==len(rows)` or positional column/row alignment (Do-NOT #7/#8). The `/execute/export/` vs bare `/execute/{id}` relationship is unverified — do not silently rewrite one path into the other in existing callers.
- **Uncharted failure surface.** Only a 200 is documented; expect at least 401 (missing/expired/invalid dev-token, by same-auth analogy to the bare sibling) plus standard 4xx for malformed SQL, an unknown `datasetId`, or insufficient dataset permissions (Do-NOT #6). Handle non-200 defensively; do not treat "spec shows only 200" as "cannot fail."
- **Credential & placeholder hygiene.** In any authored artifact use `<dataset-id>` / `<instance>.domo.com` / `<AWS_KEY>`-style placeholders; **never** commit a real developer token, session SID, bearer JWT, dataset GUID, instance hostname, or absolute user-home path. The dev-token is minted per instance (`domo-identity-access.md`) and passed inline at call time — never written into source, a handoff, or a committed example. Do not hard-code any real `datasetId` into a script (Do-NOT-style caution carried from the destructive-surface rules).
