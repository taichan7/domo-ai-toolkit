# Domo Pro Code App Skill

Use this when editing a Domo Pro Code app bundle.

## Two authoring entry points — in-product Brick editor vs local-bundle Pro Code app

Domo has **two distinct ways** to author custom code UI, and this skill's bundle rules (below) are the **local-bundle** path. A cross-ref that points here must say **which** one it means — do not conflate them, and never key routing on the bare word "DDX":

- **Local-bundle Pro Code custom app** (what the rest of this skill covers): a folder (`pro-code/manifest.json` + `index.html` + `app.js` + `app.css`) pushed with the `domo publish` CLI (ryuu). It carries a **full `manifest.json`** (aliases, mappings, dataset + Code Engine bindings), so it **can call Code Engine** and bind multiple datasets.
- **In-product Brick editor** — **Domo Bricks (formerly DDX Bricks)** authored entirely in the browser: a **Monaco** code editor opened via **Card options → Edit Card** on a Brick/DDX card `[KB]`. Preview is **Save-then-Run** — editing bound data does **not** auto-refresh the preview; you **Save** then **Run** to re-render `[KB]`. Code editing can be shared through a **Collaborators / "Share code editing with others"** modal (edit vs edit-and-share) `[KB]`.
  - **NAMING TRAP** `[KB, volatile — re-verify]`: an in-product Brick is a **simplified** app — it has **no manifest tab** and (per an open community feature request) **cannot call Code Engine**; the local-bundle app above is the one with a manifest + CE binding. The object is **"Domo Bricks (formerly DDX Bricks)"**; both entry points are legitimately "Pro Code," which is exactly why a routing arrow must name the entry point rather than the bare word "DDX".
  - **Appstore install/distribution** `[KB]`: a **GET** on an Appstore Brick installs it **and auto-runs its bundled SAMPLE dataset**; you can also **submit your own Brick to the public Appstore** (governed by the dev-portal *Appstore Requirements*). ⚠ **Egress:** publishing/submitting a Brick to the **public** Appstore distributes your **code + its sample dataset** to any instance that clicks GET, and the sample **auto-runs on install** — keep customer data, row-level content, and secrets **out of the sample dataset**.
  - **Currency** `[KB, forward-looking — re-verify]`: Domo Bricks is current and actively enhanced as of 2026 (Monaco editor, Collaborators, AI-model Bricks), and a **"Convert to App"** path turns a Brick into an App Studio app — but Domo has signalled that **App Studio Pro / Pro-Code is meant to replace the Bricks Editor** with an upgrade path and eventual deprecation, so treat Bricks-editor specifics as time-sensitive.

**No authoring REST API is claimed** for either path — the in-product editor is a browser product surface (authoring-endpoint probes returned 404/405 = **MISSING** evidence, not proof of absence) `[INFER]`; the local-bundle path deploys via the `domo publish` CLI, not a public REST author API. **Execution-safety invariants** (XSS / CSV-injection / SQL-`LIKE` / `resp.ok`) are **identical** for Brick code and bundle code and are **not** restated here — see **`## Rules`** and **`## Maintenance sweep`** below. **Open frontier:** a large Brick-parameters / Appstore-submission-requirements `[KB]` body was **not** sized this cycle and could re-open a dedicated skill at a later rank.

## Rules

- Do not put auth tokens, SIDs, cookies, API keys, or secrets in frontend code.
- Treat dataset-derived schema and row data as untrusted input in the browser. Column names, column types, and cell values arrive from the Domo Data API at runtime, and an admin can name a column `<img src=x onerror=...>`. Before interpolating any such value into `innerHTML`, run it through an HTML escaper (`& < > " '`) or build the node with `textContent` / `createElement` + `setAttribute`. Reference: `dataset-exporter/pro-code/app.js` `escapeHtml` (commit 52894c04).
  - ⚠ **A formatter is not an escaper.** A "formatted" value is only safe if the formatter *cannot* emit the raw input — i.e. it always produces digits / a fixed pattern. A **non-strict** formatter that falls back to `return value` (the original cell) on an unexpected shape leaks the raw value into the sink **even when every sibling field is escaped**, so it reads as safe but isn't. Example (F14, `inventory-management/pro-code/app.js:913`): `<small>${formatShortDate(row.date_key)}</small>` — `formatShortDate` returns its argument unchanged when the value isn't `MM-DD`-shaped, so a dataset `date_key` cell reaches `innerHTML` unescaped although the sibling `aria-label`/tooltip attributes escape it (adversarially verified, refuted:false). Fix: wrap the formatter output — `escapeHtml(fmt(x))` — or make the formatter numeric/fixed-format only (never raw passthrough). Audit the *value that lands in the sink*, not the variable name.
- Never string-interpolate untrusted schema/row values into a CSS selector (e.g. `querySelector(\`.col-checkbox[value="${col.name}"]\`)`): a `"` in the value throws a `DOMException` and silently breaks the whole feature. Instead enumerate candidate elements with `querySelectorAll` and match in JS on `el.value` / `dataset.*` — `el.value` is the DOM-decoded raw value, so it compares directly against the raw name. (`CSS.escape` also escapes selectors but yields an invalid `[value=]` for an empty string.) Reference: `dataset-exporter/pro-code/app.js` `updateSelectedColumnsState` (commit cc71cc42).
- Preserve `manifest.json` aliases and mappings.
- Use Domo aliases such as `domo.get('/data/v1/<alias>')` and `domo.post('/sql/v1/<alias>', sql, {contentType: 'text/plain'})`.
- After a raw `fetch()` (as opposed to `domo.get`/`domo.post`), always check `resp.ok` before reading the body. The `domo.*` SDK wrappers throw-convert HTTP errors, so a `try/catch` catches a 404/500; raw `fetch` does **not** reject on non-2xx (401/403/404/500) — it resolves normally, so a surrounding `try/catch` never fires. A Domo embed proxy commonly returns a JSON error envelope on auth failure, so `resp.json()` then *succeeds* and the error body flows downstream as if it were real data — a silently empty UI, or worse, an error page injected into a RAG/LLM context as "file content". Guard with `if (!resp.ok) { throw … /* or return null */ }` immediately after the fetch. References: `rag-chat-app` / `security-qa-rag-chat-app` `downloadText` (commits d438b6e1 / 203eefe8), `dataset-exporter` `initApp` (commit 530ee76d).
- When calling the Domo AI text-generation endpoint (`domo.post('/domo/ai/v1/text/generation', { input, promptTemplate: { template }, parameters })`), the `${input}` / `${context}` markers inside `promptTemplate.template` are **Domo server-side** placeholders that Domo substitutes at generation time from the request's `input` field and `parameters.*` — they are *not* JavaScript interpolation. Author the template as an ordinary quoted string (or `+` concatenation), **never a backtick template literal**: JS would evaluate `${input}`/`${context}` itself, and since those names are not in the calling scope (the params are typically `question`/`cleanContext`) it throws a `ReferenceError` and the whole call fails — or, if same-named locals happen to exist, it inlines the wrong text and Domo's own substitution never runs. The `"…"` form looks like it "should" interpolate and is a tempting false "fix" — leave it as a plain string. Reference: `rag-chat-app` / `security-qa-rag-chat-app` `generateAnswer` (commits bf6b6e90 / 978eb07f).
- In a text pipeline that both **redacts** (PII masking, profanity/secret scrubbing) and **truncates** to a length cap, run the redaction **before** the truncation — never after. Truncate-then-redact has two holes: (a) the cut can land in the middle of a match (e.g. an email split so `EMAIL_RE`'s required `\.[A-Za-z]{2,}` tail is gone), so the fragment escapes masking and the *unredacted* PII flows downstream — into the LLM context, defeating the guardrail's entire purpose; (b) a redaction token (`[REDACTED:EMAIL]`, 16 chars) is usually longer than what it replaces, so masking-after can push the string back *over* the char cap. Redact-first closes both: the boundary can then only split a harmless `[REDACTED:*]` token, and truncating already-masked text is guaranteed ≤ cap. On the happy path (text ≤ cap) the order is irrelevant, so the reorder is zero-risk. Do **not** "optimize" by truncating first to save regex work — that reintroduces the leak. Reference: `rag-chat-app` / `security-qa-rag-chat-app` `guardContext` (commit a8d07baf).
- When building a **CSV** for download, neutralize formula/CSV injection: a cell whose first character is `=` `+` `-` `@` (or TAB `\t` / CR `\r`) is evaluated as a formula/command by Excel & LibreOffice on import (`=HYPERLINK(...)`, `=cmd|'/c …'!A1`). RFC-4180 double-quoting only protects row/field **boundaries**, not against evaluation — Excel strips the quotes *then* evaluates — so quoting alone is not a defense. Prefix any such value with a `'` to force text, but **allowlist finite numbers** (`-5`, `+3.14`, `1e3`) so real data isn't corrupted, apply it to **both column headers and cell values** (headers are dataset-derived / untrusted too), and run it **before** the RFC-4180 quoting pass. This does **not** carry over to a natively-written `.xlsx`: SheetJS `aoa_to_sheet` (and peers) emit **string-typed** cells — a formula cell needs an explicit `<f>` / `.f` element — and Excel renders string cells literally, never formula-evaluating them. Neutralizing xlsx is therefore unnecessary **and** corrupts fidelity: a programmatic string keeps the `'` as a literal character (not Excel's invisible `quotePrefix`), so `'=SUM(…)` shows the stray apostrophe = a regression. A third CSV-shaped case completes the rule: a `text/csv` string assembled to **upload to a dataset-ingest API** (browser→Code Engine→Domo `…/uploads`), rather than to hand a human a file, is also **not** neutralized — the ingest stores each cell as data and never formula-evaluates it, so prefixing `'` there only corrupts stored values (a legit `-5`, or a `=`/`-`-leading info line). Neutralization keys off the **destination** — a spreadsheet app that evaluates formulas on open — not off the `.csv` extension or the `text/csv` MIME type; do not grep-match a CSV-building function and "fix" an ingest path. Keep the CSV-neutralized / xlsx-untouched asymmetry; do not "align" them. References: `dataset-exporter/pro-code/app.js` `csvNeutralize` + `downloadCSV` / `downloadExcel` (commits 52894c04, 2299f91e) for the download path; `soccer-team-tools/code-engine/formation_save_service.js` `toCsv` / `csvEscape` for a correctly-non-neutralized ingest path (RFC-4180 quoting only).
- When building a SQL `LIKE` filter from a user-supplied search value, escaping the value's single quotes (`'`→`''`) stops string-literal breakout but is **not** sufficient: `%` and `_` are LIKE **metacharacters**, so a literal `%`/`_` in the search term silently widens the match (`50%` matches anything starting `50`; `a_c` matches `abc`, `axc`, …). This is a **correctness** bug, *not* an injection one — the quote-escaping already blocks injection; the value sits inside a quoted string literal and `%`/`_` can only alter pattern matching, never SQL structure. If the field is meant to be a *contains* match, escape `%`, `_`, and the escape char itself in the value and append an `ESCAPE '\'` clause (`… LIKE '%'‖:v‖'%' ESCAPE '\'` — ANSI-standard, supported by Domo's `/sql/v1/` Presto/Trino engine); if wildcard search is genuinely intended, document that. Do **not** "fix" this by piling on more quote-escaping — that targets a different, already-closed hole. Reference: `dataset-exporter/pro-code/app.js` `buildSql` builds `LIKE '%${safeVal}%'` with quote-escaping only.
- Keep AppDB, Dataset, Code Engine, and Workflow responsibilities separated.
- Avoid moving heavy business logic into the browser when Code Engine or dataflows already own it.
- Respect Domo embed constraints: app size, iframe behavior, refresh, and no uncontrolled external navigation.
- Follow existing visual design and layout unless the user asks for a redesign.
- For a full `app.js` / `index.html` rewrite, do not emit the whole file in one write; write a minimal version with unique placeholders first, then fill it with a few small edits (otherwise a truncated response leaves a half-written bundle). See `AGENTS.md` → "Writing Large Files".
- Do not run `domo publish` without explicit user confirmation.

## Publishing a design — `domo publish` **is** the designs REST API (not ryuu-only, not OAuth-gated)

`domo publish` (ryuu) has **no magic**: it is a thin client over a **designs REST API**, so a design can be (re)published with **any valid Domo auth** — a **SID** minted from an OAuth refresh token *or* an `X-DOMO-Developer-Token` — **without** the `domo` CLI and **without** an interactive browser login. (The toolkit's `SKILL.md §9` "Pro Code Apps are … **not** API driven" is misleading: the instance stores the uploaded bundle, and the bundle is uploaded **via this API**.) Verified by reading ryuu's own client (`.../node_modules/ryuu-client/lib/domoapps-client.js`); `DESIGNS_BASE_URL = /api/apps/v1/designs`:

| ryuu step | REST call |
|---|---|
| create design (new; manifest has no `id`) | `POST /api/apps/v1/designs?path=manifest.json` — body = manifest JSON → returns `{id}` |
| get design + versions | `GET /api/apps/v1/designs/{id}?parts=versions` → `{latestVersion, versions[]}` |
| **upload one asset** | **`POST /api/apps/v1/designs/{id}/versions/{version}/assets?path={relpath}`** — body = **raw file bytes**; `Content-Type` by extension (map below); `maxBodyLength: Infinity` |
| publish all assets (`uploadAllAssets`) | `manifest.json` first (`JSON.stringify(manifest)`), then `glob('**/*')` minus `node_modules` + `manifest.ignore` + directories, each via the asset POST, `version = manifest.version` (25 at a time) |
| release — **App-Store only, NOT needed for a normal publish** | `PUT /api/apps/v1/designs/{id}/versions/{version}/release` |

So publishing is a **per-file POST**, not a zip upload. Uploading to a *new* `{version}` string creates that version; a card bound **`FOLLOW_LATEST`** re-renders the new latest with **no re-embed**. A reusable REST publisher only needs a client holding a SID/token for the target instance — e.g. `inventory-management-app/scripts/provision_domo.py`'s `DomoClient` already mints a SID from the ryuu configstore refresh token (that is exactly why read-only `verify` works against an OAuth-only instance). Replicate `uploadAllAssets` with raw POSTs — do **not** route the bytes through a JSON client (`provision_domo.py`'s `request()` JSON-encodes the body; send raw bytes + the extension's content-type yourself).

**Two real non-blockers that are easily mistaken for hard blockers (this is the misunderstanding this section exists to kill):**
- **An OAuth-only instance** — ryuu login file (`~/.config/configstore/ryuu/<inst>.json`) has `devToken:false` and only a `refreshToken` (e.g. `maintenance-instance`) — makes **`domo login -i <inst>` drop to an interactive developer-token prompt** that can't be answered headlessly. That blocks the *CLI*, **not** publishing: mint a SID from the same refresh token (`POST /api/oauth2/token` → `GET /api/oauth2/sid`) and POST the assets. OAuth ≠ "can't publish without a human."
- **ryuu's "current instance" is a machine-shared singleton** (no per-command override — `domo publish` takes only `-g`/`-d`), so switching it with `domo login` collides with other local sessions deploying elsewhere. REST publish is **per-request authed**, sidestepping the shared CLI state entirely.

**`CONTENT_TYPE_MAP` gotcha (served vs 0-byte live).** The asset POST sets `Content-Type` only for extensions in ryuu's map — `html css js map json jsx ts tsx vue py md sass sh sql toml xml yaml yml` + images `png jpg jpeg gif svg ico webp bmp tiff tif eps`. **`.mjs`, `.LICENSE`, `.txt` are NOT in the map** → they upload with no content-type and **serve as 0-byte live** (harmless if unreferenced, broken if a runtime file). Keep runtime assets to mapped types and `manifest.ignore` dev-only files (tests, licenses). After publish, confirm with `GET /api/apps/v1/designs/{id}?parts=versions` (`latestVersion` bumped) and `domo download -i <id> -d latest` byte-diff. See the reference apps' setup guides for the provisioning, publish and App Studio embedding sequence.

## Regression-testing the pure security helpers

`node --check` only proves the file parses. To *lock* the security invariants above (`escapeHtml`, `csvNeutralize` + the CSV/xlsx asymmetry, `quoteSqlIdent`, redact-before-truncate) so a later edit can't silently regress them, add a characterization test — **without** touching `app.js` (so no `domo publish` gate) and **without** a DOM.

The obstacle: `app.js` is a non-module browser script whose *top level* is DOM-coupled — it builds a `ui` object from `document.getElementById(...)`, attaches `addEventListener`s, and calls `DOMContentLoaded` at load. So `require()`-ing it, or `vm`-running the whole file, throws `document is not defined` before any helper is reachable. The pure helpers themselves, however, take only their arguments.

Technique (repo convention = `node:test` + `node:assert/strict`, run via `node <path>`): read `app.js` as text, **brace-match-extract** just the target function's source (`function <name>(` → scan for the balanced closing `}`), then evaluate that one function in a bare `vm` context and grab it as the script's completion value:

```js
const fn = vm.runInContext(extractFunction('csvNeutralize') + '\n' + 'csvNeutralize;', vm.createContext({}));
```

No DOM, no network, no top-level side effects — just the pure function under test. Then assert behavior (formula chars prefixed, finite numbers allow-listed, `&`-first escaping, `"`→`""` doubling). For invariants that live in *control flow* rather than a single return value — e.g. "`downloadCSV` neutralizes header **and** value, `downloadExcel` neutralizes neither" and "neutralize runs **before** RFC-4180 quoting" — extract the enclosing function's source and assert on the **text** (call count via `.match(/csvNeutralize\(/g)`, `indexOf` ordering, `assert.doesNotMatch`). Caveat: the brace scanner assumes the extracted function has no *unbalanced* `{`/`}` inside a string / regex / comment (true for these helpers — template-literal `${…}` pairs close); guard with `assert.ok(text.endsWith('}'))` so an extraction miss fails loudly instead of silently testing the wrong slice. Reference: `dataset-exporter/tests/test_export_neutralizers.js` (commit a4b69ca1).

**Module-dependency variant** (when the helper is DOM-free but *not* purely its arguments): some security helpers read module-level state — e.g. `guardContext` references a compiled `EMAIL_RE`/`PHONE_RE` and a `SETTINGS` object, not just its parameter. Extend the technique two ways. (a) For a constant you must *reproduce faithfully* (a regex whose exact pattern is the thing under test), pull its `const NAME = …;` line straight from source (`SOURCE.match(new RegExp('const\\s+' + name + '\\s*=[^\\n]*;'))`, guard `.endsWith(';')`) and prepend it to the vm script — the test then exercises the **real** regex, so a later edit to the pattern is caught instead of silently diverging from a hand-copied duplicate. (b) For state you want to *vary per test* (`SETTINGS.mask_pii`, `SETTINGS.max_context_chars`), inject it as a **context global** — `vm.createContext({ SETTINGS: {…}, console: { warn(){} } })` (stub any `console` the `catch` uses) — and re-load the extracted function per case; the function closes over the context global. This lets an invariant like redact-before-truncate be exercised *behaviorally*, not just as a source-text ordering assertion: feed an input where an email straddles the char cap (`'x'.repeat(20) + 'user@example.com' + 'y'.repeat(100)`, `max_context_chars: 30`) and assert the raw fragment (`user@`, `@examp`) is absent — redact-first masks it, truncate-first would leak it. Pair that with the text-level `mask.indexOf < slice.indexOf` check so both the behavior and its source ordering are locked. Reference: `rag-chat-app` / `security-qa-rag-chat-app` `tests/test_guard_helpers.js` (commits 6ed1148f / ee503f61).

**Arrow-const variant** (when the helper is a nested `const NAME = (…) => {…}`, not a top-level `function` declaration). Shared Code Engine services — and some app bundles — keep their pure helpers as **arrow-consts nested inside an outer function**, where the `function\s+name\s*\(` extractor above finds nothing and the whole file can't be run (a CE module does `require('codeengine')` at top level). Example: `soccer-team-tools/code-engine/formation_save_service.js` defines `csvEscape` / `toCsv` / `normalizeRecord` / `escapeSql` inside `async function save_formation_records(...)`. Extract the single `const NAME = …;` **statement** instead: find `const NAME =`, locate the `=>`, then (a) if the arrow body opens with `{`, brace-match to its close and swallow a trailing `;`; (b) otherwise it's an *expression body* one-liner (`const escapeSql = (v) => String(v||'').replace(/'/g,"''");`) — take through the first `;` after the arrow. Then the crucial difference from the `function`-declaration case: **`const` is not hoisted**, so when a helper calls another (`toCsv` calls `csvEscape`) you must prepend the dependency consts in **dependency order**, not any order — a `function`-hoist harness that ignores order will `ReferenceError`. The same brace-scanner caveat carries over (assumes no unbalanced `{`/`}` inside a string / regex / comment — verified true here: `csvEscape`'s `/[",\n\r]/` regex and its template `${…}` pairs are balanced), so keep the `assert.ok(text.endsWith('}'))`-style guard for the block-body form. This lets you lock a **shared** service that both mirror apps write through but that had **zero** coverage — including the deliberately-**non**-neutralized ingest CSV contract (the CSV rule above) so a later "add formula-neutralization" edit fails loudly. Reference: `soccer-team-tools/code-engine/tests/test_save_service_serializers.js` `extractConstArrow` (commit 705ac0f1).

**Cross-realm caveat for object/array return values:** a helper that returns a *primitive* (string / number / boolean) compares cleanly, but one that returns an **object or array built inside the vm context** carries *that context's* `Object.prototype` / `Array.prototype`, not the test realm's. Under `node:assert/strict`, `assert.deepEqual` is `deepStrictEqual`, which checks prototype identity — so it fails with `ERR_ASSERTION` **even when every key and value is identical**, printing structurally-equal `actual` / `expected` (a genuinely confusing miss that looks like a value bug but isn't). Shallow-copy the return into a test-realm object before comparing — inline `assert.deepEqual({ ...fn(x) }, {…})`, or a small `const plain = (o) => (o !== null && typeof o === 'object' ? { ...o } : o);` helper so the null / primitive branches (which use `assert.equal`) pass through untouched. This is a *test-harness* fix, not a change to the locked behavior — the `{…}` structure and values are still what you characterize. (Primitive-returning helpers like `escapeHTML` never hit this — the pitfall is specific to object/array returns crossing the vm realm boundary.) **The shallow copy only rescues a *flat* return.** For a **nested** return — an array of objects, or an object whose values are themselves objects — `{ ...fn(x) }` both loses array-ness (`{ ...[{a:1}] }` → `{ 0: {a:1} }`) and, being shallow, leaves every *inner* object on the sandbox prototype, so `deepStrictEqual` keeps failing. Compare a fully-serialized shape instead: `const shape = (v) => JSON.stringify(v); assert.equal(shape(actual), shape(expected))` is deep and prototype-agnostic (JSON also pins key **insertion order**, which is often the very thing you want to characterize). Keep a reference-identity `assert.equal(fn(x), x)` for any bare-passthrough branch where the input object is returned unchanged (that value is host-realm, so `===` is the strongest check). References: `soccer-team-tools/soccer-squad-manager/tests/test_pure_helpers.js` `plain()` for a flat single-object return (commit cf952e3f); `dataset-exporter/tests/test_export_neutralizers.js` `shape()` for the array-of-objects `normalizeSqlResult` return (commit 450cd7c6).

This is a *characterization* test — it fixes "what the code does now", so it's the regression net you add *before* a refactor, not a spec you write first.

## Maintenance sweep (auditing an existing bundle)

When reviewing an already-shipped bundle (rather than writing new code), run this grep-driven checklist. Each `grep` yields the candidate sites; confirm every site satisfies the paired invariant. **Sites already confirmed clean must NOT be "re-fixed"**: a second `resp.ok` check, an `&amp;amp;` from double-escaping, a redundant `try/catch` are all churn and can regress display. The sweep is for NEW code, or a bundle whose invariants were never verified — a clean pass is a valid outcome, not a prompt to manufacture a change.

**Two method footguns that make this sweep lie "clean" (both are over-claims — as bad as missing a real bug):**
- **A silent `grep` is not a clean `grep`.** `grep` exits **1** for "no match" but **2** for an *error* (bad pattern, unreadable path, a word-split argument list) — and an idiom like `grep -nE 'pat' $FILES 2>/dev/null || echo "(none)"` prints the same `(none)` for both, so a *broken* grep reads as a *clean* result. Check the exit code (`echo "exit=$?"`; `2` ≠ `1` ≠ `0`). Never pass a multi-file set as an **unquoted** `$FILES`; sweep a set with `git ls-files '<glob>' | tr '\n' '\0' | xargs -0 grep -nE …` or a per-file quoted loop, and back any "0 hits" claim with the `git ls-files` denominator. When you find one false-clean, re-run every same-idiom grep from that session. (2026-09-06: an unquoted-`$FILES` fetch sweep exited 2 and nearly concluded "no raw fetch in scope" — 5 in-scope files did use it.)
- **A "fixed" file is not a clean file — count sinks, not files.** A fix commit repairs the *one* sink it targeted; the same file can hold *other* sinks the fix never touched. Enumerate per file (`grep -n '\.innerHTML' <file>`) and verify **every** sink before calling the file clean; a coverage table listing files as "fixed / verified-clean" is only trustworthy if each row was checked at **sink** granularity, not file granularity. (2026-09-06 F15: `dataset-exporter/pro-code/app.js` was carried as "fixed" from the F2 `renderColumnsList` repair, but its error-path sink at `:192`/`:197` — `userMessage += ': ' + err.message` → `innerHTML` — was never escaped; low-severity / defense-in-depth, `domo publish`-gated.)

- Raw `fetch`: `grep -nE '(await |= )(window\.)?fetch\(' pro-code/app.js` — every hit needs an `if (!resp.ok)` guard immediately after (or is a `domo.*` SDK call, or an intentional test-harness poll). See the `resp.ok` rule above.
- `JSON.parse`: `grep -nE 'JSON\.parse\(' pro-code/*.js` — every hit sits inside `try/catch`; for `sessionStorage` / AppDB / Code Engine payloads also validate the parsed type (e.g. `typeof x === 'object'`) before use, so a legacy or corrupt value falls to the catch instead of white-screening the app.
- DOM-XSS sinks: `grep -nE 'innerHTML|insertAdjacentHTML|outerHTML' pro-code/app.js` — every dynamic value (dataset column names / types / cells, LLM output, AppDB / CE responses, contact names, user input) is routed through `escapeHtml` (`& < > " '`) or built with `textContent` / `createElement` + `setAttribute`. A value placed inside a `<textarea>` still needs escaping (`</textarea>` breakout).
- `promptTemplate.template`: it must be a plain quoted string, never a backtick template literal — `${input}` / `${context}` are Domo server-side markers, not JS interpolation (see the AI text-generation rule above).
- Redact-before-truncate: `grep -nE 'slice\(0|substring\(0|REDACTED|(EMAIL|PHONE|PII)_RE' pro-code/app.js` — if one function both truncates to a length cap (`slice(0, max)` / `substring(0, n)`) and masks/redacts, confirm the mask runs **before** the slice, not after (see the redact-before-truncate rule above). Truncate-first can split a PII match past its regex anchor and leak the unmasked fragment downstream, and a `[REDACTED:*]` token can also overflow the cap. Reordering is zero-risk on the happy path (text ≤ cap).
- CSV / formula injection: `grep -nE 'aoa_to_sheet|csvNeutralize|new Blob\(|toDataURL|download.*[Cc]sv|\.csv' pro-code/app.js` — if the app assembles a **CSV** string for download, every cell **and header** must pass a neutralizer that prefixes `'` to values starting `= + - @ \t \r` (number-allowlisted), applied **before** RFC-4180 quoting. A native `.xlsx` writer (`aoa_to_sheet`) needs **no** neutralization — its string cells aren't formula-evaluated and adding it corrupts data. A `text/csv` string built to **upload to a dataset-ingest API** (e.g. a Code Engine save service, `…/uploads`) also needs **no** neutralization — ingest stores cells as data, and `'`-prefixing corrupts them; neutralize only the human-download-to-spreadsheet path. See the CSV/xlsx rule above; do not "align" the paths.
- SQL `LIKE` from user input: `grep -niE '\bLIKE\b' pro-code/app.js` — for every user-supplied search value interpolated into a `LIKE` pattern, escaping the value's `'`→`''` (which blocks injection) is **not** enough: the `%` and `_` LIKE metacharacters must **also** be escaped (plus the escape char) with a trailing `ESCAPE` clause, or a literal `%`/`_` in the term silently widens the match — a **correctness** bug. See the `LIKE`-escaping rule above; this is orthogonal to the quote/CSV rules — do not "fix" it by adding more quote-escaping. (In this repo: `dataset-exporter` `buildSql`, tracked as F5, fix `domo publish`-gated.)
- Doc ↔ manifest ↔ schema consistency: cross-check every *concrete* claim in `README.md` / `docs/*.md` (versions, column counts and order, dataset / design / package IDs, CE function name + parameter count, workflow aliases and `startName`s) against `pro-code/manifest.json` and any `dataset/*.schema.json` mirror. Docs drift silently; a specific number / ID / alias that no longer matches the source of truth is a real (if low-severity) defect. This method surfaced genuine gaps (`author_name`, `csvNeutralize`, a dead-config column) in this repo. **One caveat before flagging a *version* mismatch**: a bundle carries *two independent* versions — the app-bundle version (manifest top-level `version`) and each Code Engine package version (`packagesMapping[].version`) — and a README may correctly cite the *CE package* version, which differs from the bundle version by design. Confirm which one a doc string refers to before calling it drift: "aligning" a CE-package version to the bundle version (or vice-versa) introduces a defect instead of fixing one. Reference: `soccer-team-tools` READMEs cite `save_formation_records` **v1.0.4** = the CE package (`packagesMapping[].version`), while the app bundles are manifest `0.0.4` / `0.0.3` — both correct, not drift.
- Mirror-pair apps: when two apps are intentional mirrors (e.g. `rag-chat-app` ↔ `security-qa-rag-chat-app`), a fix applied to only one is a latent bug in the other. Detect drift by diffing the function inventory (`diff <(grep -oE 'function[[:space:]]+[A-Za-z_$][A-Za-z0-9_$]*' A | sort -u) <(… B …)`) and the CSS selector inventory; apply every logic fix to both siblings.
